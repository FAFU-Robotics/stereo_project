## 0. 一句话结论

**两个物理相机（HP 内置 + DECXIN）在 DirectShow 层面返回 `E_ACCESSDENIED(0x80070005)`，
即"Windows 帧服务器拒绝了本进程的相机访问"**；唯一能打开的是 **HP 的软件虚拟摄像头**
（`OMEN Cam ＆ Voice`），它不出真实画面。时间线显示：**9/29 16:04 你的 Python 还能正常用相机，
9/29 18:53 HP OMEN 一整套助手进程启动之后就不能用了**。

## 2. DECXIN 的真实能力清单（驱动向 DirectShow 声明）

用 `IAMStreamConfig::GetNumberOfCapabilities/GetStreamCaps` 直接问驱动（`_work/DShowCaps.cs`）：

| 索引 1 = USB Camera（DECXIN） | 分辨率 | 格式 |
|---|---|---|
| | 2560x960 | MJPG / YUY2 |
| | 2048x768 | MJPG / YUY2 |
| | 2560x720 | MJPG / YUY2 |
| | 1920x540 | MJPG / YUY2 |
| | 1600x600 | MJPG / YUY2 |
| | **1280x480** | MJPG / YUY2 |
| | 640x240 | MJPG / YUY2 |

**关键推论：全部为 8:3 超宽比例，即"左右拼接"双目布局**：
- `1280x480` = 2 × **640×480**（每只眼 640×480，最适合接 FFS）
- `2560x720` = 2 × 1280×360
- `640x240` = 2 × 320×240
- **它不提供 640x480 这类单幅分辨率** —— 之前所有探测都在请求不存在的格式

对照：索引 0（HP 内置）声明 9 种 YUY2 格式（640x480 / 1280x720 / 1920x1080 …）；
索引 2（HP 虚拟摄像头）**连 `IAMStreamConfig` 都没有**（`InvalidCastException`），证明它不是真相机。

## 11.4 当前结论

**这台机器上"非打包（桌面）应用程序"的物理相机访问被系统拒绝**，
而"打包应用"（Windows 相机 App）可以正常使用同一台 DECXIN 相机。

所有其它可能都已被实测排除。剩下能解释该现象的只有
**相机隐私/能力授权（ConsentStore）中"桌面应用"这一分支处于异常状态**——
尽管注册表读出来是 `Allow`，但**有效状态可能已损坏**
（Windows 对这种不一致的官方修复方式就是**把开关关掉再打开**，强制重写授权记录）。
