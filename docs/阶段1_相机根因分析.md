# 阶段 1 根因分析 —— 相机"打不开/全黑"的完整证据链

> 时间：2026-09-30　执行人：DSH 助手
> 全部结论均来自本机实测；每一条都附取证方式。**未修改任何驱动、注册表或相机配置。**

## 0. 一句话结论

**两个物理相机（HP 内置 + DECXIN）在 DirectShow 层面返回 `E_ACCESSDENIED(0x80070005)`，
即"Windows 帧服务器拒绝了本进程的相机访问"**；唯一能打开的是 **HP 的软件虚拟摄像头**
（`OMEN Cam ＆ Voice`），它不出真实画面。时间线显示：**9/29 16:04 你的 Python 还能正常用相机，
9/29 18:53 HP OMEN 一整套助手进程启动之后就不能用了**。

## 1. 设备清单与索引映射（两条独立路径互相印证）

| 索引 | 设备名 | 类型 | 设备路径 |
|---|---|---|---|
| 0 | HP True Vision FHD Camera | 物理（笔记本内置） | `\\?\usb#vid_0408&pid_548d&mi_00#...` |
| **1** | **USB Camera** | **物理（= 你的 DECXIN）** | `\\?\usb#vid_0bda&pid_5883&mi_00#...` |
| 2 | OMEN Cam ＆ Voice | **软件虚拟摄像头（HP）** | （无设备路径） |

取证方式：
- 自写 C# 调用 DirectShow `ICreateDevEnum` 枚举（`_work/DShowEnum.cs`）
- `pygrabber`（comtypes 绑定）`get_input_devices()` —— **结果与上表完全一致**

## 2. DECXIN 的真实能力清单（驱动向 DirectShow 声明）

用 `IAMStreamConfig::GetNumberOfCapabilities/GetStreamCaps` 直接问驱动（`_work/DShowCaps.cs`）：

| 索引 1 = USB Camera（DECXIN） | 分辨率 | 格式 |
|---|---|---|
| | 2560x960 | MJPG / YUY2 |
| | 2048x768 | MJPG / YUY2 |
| | 2560x720 | MJPG / YUY2 |
| | 1920x540 | MJPG / YUY2 |
| | 1600x600 | MJPG / YUY2 |
| | **1280x480** | MJPG / YUY2 |
| | 640x240 | MJPG / YUY2 |

**关键推论：全部为 8:3 超宽比例，即"左右拼接"双目布局**：
- `1280x480` = 2 × **640×480**（每只眼 640×480，最适合接 FFS）
- `2560x720` = 2 × 1280×360
- `640x240` = 2 × 320×240
- **它不提供 640x480 这类单幅分辨率** —— 之前所有探测都在请求不存在的格式

对照：索引 0（HP 内置）声明 9 种 YUY2 格式（640x480 / 1280x720 / 1920x1080 …）；
索引 2（HP 虚拟摄像头）**连 `IAMStreamConfig` 都没有**（`InvalidCastException`），证明它不是真相机。

## 3. 访问被拒的精确位置与错误码

用 `pygrabber` 建标准 DirectShow 采集图，逐步打印结果：

| 设备 | `add_video_input_device`（绑定过滤器 + `IFilterGraph::AddFilter`） |
|---|---|
| 索引 0（物理） | ❌ `HRESULT=0x80070005` = **E_ACCESSDENIED** |
| 索引 1（物理） | ❌ `HRESULT=0x80070005` = **E_ACCESSDENIED** |
| 索引 2（虚拟） | ✅ 成功，抓到 20 帧（1920x1080 RGB24，内容全黑） |

辅助证据：自写 C# 测试证明**绑定 `IBaseFilter` 这一步是成功的**（三个设备都 OK），
所以被拒的是**把过滤器加入图/初始化设备**这一步 —— 物理 UVC 相机会经
**Windows Camera Frame Server** 做权限仲裁，`E_ACCESSDENIED` 正是帧服务器拒绝的签名。

## 6. 剩余假设（按可能性排序，都需要人工确认）

1. **HP OMEN 的摄像头/虚拟摄像头功能独占了物理相机**（最可能）。
   HP 助手用 MF 打开物理相机 → 通过 `OMEN Cam & Voice` 转发 → 其他程序访问物理相机被拒。
   这也能解释"相机 App 能出画面"：App 里看到的很可能是 **OMEN 虚拟摄像头**而不是 DECXIN。
2. **HP 的摄像头隐私键/隐私功能**（部分 HP 机型 F8 切换）在驱动层屏蔽访问。
   特征与 E_ACCESSDENIED 相符，且设备仍显示"正常"。
3. 物理相机在 DirectShow 路径下确实不出流（USB 端口/线材），需换机身 USB3 口直插复测。

# 10. 后续验证（2026-09-30 下午，两条新的否定结果 + 一个新问题）

## 10.1 否定结果 1：不是"HP 助手进程占用相机"

用户授权后准备结束 `HP.OMEN.VirtualCamHelper` / `HP.OMEN.VadRedirectHelper`，
结果发现**这两个进程（以及 `OmenCommandCenterBackground`）此时已经不在运行**。
在这两个进程**不存在**的情况下重测：

```
[1] USB Camera   ->  add_video_input_device 失败: HRESULT=0x80070005 (E_ACCESSDENIED)
```

**结论：HP 的用户态助手进程不是原因**（但 HP 的内核驱动与服务仍在运行，见 10.3）。

## 10.2 否定结果 2：不是"相机类过滤驱动"

```
相机类(Camera) UpperFilters : ksthunk          <- 微软标准，非厂商
图像类(Image)  UpperFilters : ksthunk
设备实例 Device Parameters   : 无 UpperFilters / LowerFilters
```
**结论：HP 没有给相机类挂过滤驱动。**

## 10.3 新问题：帧服务器已停止（需管理员处理）

```
sc query FrameServer        ->  STATE : 1  STOPPED
sc query FrameServerMonitor ->  STATE : 1  STOPPED
```

**重要时间矛盾**：今天 11:05 第一次检查时 `FrameServer` 是 **Running**，
而当时物理相机**已经**打不开。所以：

- 帧服务器停止 **不是**最初故障的原因（它是后来才停的，可能是 HP 进程退出或多次异常访问导致）；
- 但它**现在是一个必须解决的额外障碍**：帧服务器不运行，物理相机一定无法被访问；
- 当前会话不是管理员（`IsInRole(Administrator) = False`），无法启动该服务。
